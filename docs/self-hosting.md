# 자체 호스팅 (MOTIS)

naeryeo의 경로 검색을 **여러분의 장비에서 직접 돌리는** 방법입니다. 상용 경로 검색 API의
계정도, 앱키도, 과금 정책도 필요 없습니다.

이 문서의 절차와 수치는 2026년 8월 3일에 **실제로 한 번 끝까지 수행하며** 측정한 것입니다.
사용한 조합은 MOTIS 2.11.0 + KTDB 전국 GTFS + Geofabrik 대한민국 OSM이고, 검증에 쓴
질의와 결과는 [9절](#9-구축-완료-판정)에 있습니다.

## 1. 무엇을 얻고 무엇을 감수하는가

**얻는 것**: 경로 검색이 외부 사업자의 과금 정책·무료 한도·약관 변경에 영향받지 않습니다.
호출 횟수 제한이 없고, 어떤 질의를 했는지가 외부로 나가지 않습니다.

**감수하는 것**: 엔진과 데이터의 운영 책임이 여러분에게 있습니다. 실시간 정보가 없고,
경로·소요시간이 상용 서비스와 다를 수 있습니다. 특히 현재 공개된 국내 GTFS는 **2023년 3월
기준**이라 최신 노선 개편이 반영돼 있지 않습니다 — [6절](#6-데이터의-한계)을 반드시 읽으세요.

## 2. 준비물과 자원 요구치

### 2-1. 먼저 갖춰야 할 것

**저장소 체크아웃이 필요합니다.** 이 문서의 `deploy/motis/` 구성 파일들은 릴리스 바이너리에
들어 있지 않습니다. naeryeo를 바이너리로만 설치했더라도 자체 호스팅을 하려면 소스를 받아야
합니다.

```bash
git clone https://github.com/GyeongHoKim/naeryeo.git
cd naeryeo
```

**naeryeo 실행 파일**도 필요합니다([5절](#5-naeryeo와-연결)에서 씁니다). 이미 설치돼 있다면
그대로 쓰고, 없다면 방금 받은 소스에서 만들 수 있습니다.

```bash
go build -o naeryeo ./cmd/naeryeo
```

**Docker**는 `docker compose`(하이픈 없는 형태)가 동작하는 버전이면 됩니다. 검증 환경은
Docker 29.4.0 / Compose v5.1.2였습니다. 컨테이너 이미지는 `linux/amd64`와 `linux/arm64`를
모두 제공하므로 Intel·Apple Silicon 어느 쪽이든 됩니다.

### 2-2. 자원 요구치

아래는 추정치가 아니라 실측값입니다. 측정 환경은 Apple Silicon macOS, 물리 RAM 16 GB,
Docker Desktop에 **VM 메모리 7.82 GB / 10 vCPU**가 할당된 상태였습니다.

| 항목 | 실측값 |
| --- | --- |
| 다운로드 | 약 710 MB (OSM 284 MB + GTFS 211 MB + 컨테이너 이미지 215 MB) |
| 그래프 빌드 소요 시간 | **55초** |
| 그래프 빌드 최대 메모리 | **3.98 GiB** |
| 결과 디스크 | **1.5 GB** (원본 입력 별도) |
| 총 디스크 여유 권장 | **5 GB** (빌드 중 임시 공간 포함) |

**메모리는 컨테이너에 8 GB를 줄 수 있어야 합니다.** 실측 최대치가 3.98 GiB이지만 그 수치를
그대로 한도로 잡지 마세요 — 측정은 7.82 GB가 할당된 환경에서 나온 값이고, 여유가 없으면
빌드가 도중에 OOM으로 죽습니다. Docker Desktop을 쓴다면 Settings → Resources에서 먼저
확인하세요. 최소선을 잡아야 한다면 6 GB이며, 4 GB는 실패합니다.

빌드 시간은 CPU 코어 수에 크게 좌우됩니다. 위 55초는 10 vCPU 기준이며, 2코어 장비에서는
수 배로 늘어날 수 있습니다. 시간의 대부분은 도로망(`osr`) 전처리가 씁니다.

**전체 소요 시간은 GTFS 확보에 달려 있습니다.** 아래 빌드 작업 자체는 한 시간 안쪽이지만,
공식 경로로 GTFS를 받으려면 신청·승인 절차를 거쳐야 하고 그 소요는 예측할 수 없습니다
([3-1절](#3-1-대중교통-시간표-gtfs)).

> 이 수치는 **지도 타일 생성을 끈** 설정([4절](#4-엔진-실행))에서 측정한 것입니다.
> `motis config`가 자동 생성하는 기본 설정은 256 GB짜리 타일 데이터베이스를 켜므로
> 시간·디스크가 전혀 다른 규모가 됩니다. naeryeo는 타일을 쓰지 않습니다.

## 3. 데이터 확보

두 파일이 필요합니다. `deploy/motis/data/` 에 **아래 이름 그대로** 저장하세요 —
`deploy/motis/config.yml`이 이 이름을 참조하므로, 이름이 다르면 빌드가 입력을 찾지 못합니다.

`data/`는 git에 포함되지 않으므로 직접 만들어야 합니다.

```bash
mkdir -p deploy/motis/data
```

### 3-1. 대중교통 시간표 GTFS

저장할 이름: **`ktdb-gtfs.zip`**

**공식 경로 (권장)**: 국가교통DB(KTDB)가 전국 GTFS를 제공합니다.

- 안내 공지: [(안내) 2023년 3월 기준 GTFS 기반정보 제공 안내](https://www.ktdb.go.kr/www/selectBbsNttView.do?key=45&bbsNo=2&nttNo=3764)
- 신청 경로: [국가교통DB](https://www.ktdb.go.kr) → 정보공개 → 자료신청 →
  교통분석자료 신청 → 교통망 GIS DB → 대중교통 → 대중교통

직접 다운로드 링크가 아니라 **자료신청 절차**입니다. 회원 가입과 한국어 메뉴 탐색이
필요하고, 신청 후 이용자 만족도 조사를 거쳐 내려받습니다. **승인까지 걸리는 시간은 KTDB가
공지하지 않으므로 예측할 수 없습니다** — 같은 날 끝나지 않을 수 있다고 보고 일정을 잡으세요.

받은 파일은 이름이 무엇이든 **`ktdb-gtfs.zip`으로 바꿔** `deploy/motis/data/`에 두면 됩니다.

```bash
mv ~/Downloads/<받은파일>.zip deploy/motis/data/ktdb-gtfs.zip
```

zip 안에 `agency.txt`·`calendar.txt`·`routes.txt`·`stop_times.txt`·`stops.txt`·`trips.txt`가
바로 들어 있어야 합니다(하위 폴더 없이). 확인:

```bash
unzip -l deploy/motis/data/ktdb-gtfs.zip | head
```

**미러 (참고)**: 오픈소스 프로젝트 [Transitous](https://github.com/public-transport/transitous/blob/main/feeds/kr.json)가
같은 데이터의 미러를 유지합니다. 링크가 가리키는 것은 내려받을 파일이 아니라 **피드 정의
JSON**이며, 그 안의 `url` 필드에 실제 내려받기 주소가 들어 있습니다. 개인이 관리하는 공유
링크라 **언제든 사라질 수 있으므로** 1순위로 삼지 마세요. 원본은 어디까지나 KTDB입니다.

검증에 쓴 미러 파일은 압축 211 MB, 풀면 약 1.48 GB였습니다. 받은 파일이 이보다 훨씬 작다면
받다 만 것입니다.

### 3-2. 도로·보행 네트워크 OSM

저장할 이름: **`south-korea-latest.osm.pbf`**

```bash
curl -fL -o deploy/motis/data/south-korea-latest.osm.pbf \
  https://download.geofabrik.de/asia/south-korea-latest.osm.pbf
```

`-f`를 빼지 마세요. 서버가 오류를 돌려줘도 `curl`이 그 오류 페이지를 올바른 파일명으로
저장해 버려, 한참 뒤 빌드 단계에서야 이상하게 실패합니다.

내려받은 뒤 크기를 확인하세요. 2026-08-03 기준 약 **284 MB**였고, 수십 MB에 그친다면
받다 만 것입니다.

```bash
ls -lh deploy/motis/data/south-korea-latest.osm.pbf
```

출처: [Geofabrik south-korea](https://download.geofabrik.de/asia/south-korea.html) — **매일
갱신됩니다.** 즉 이 파일은 버전이 고정돼 있지 않아, 다른 날 받으면 다른 그래프가 나옵니다.
정확히 같은 결과를 재현해야 한다면 Geofabrik이 함께 제공하는 날짜별 스냅샷을 쓰세요.

**이 파일은 선택이 아닙니다.** naeryeo는 모든 장소 이름을 엔진의 `/api/v1/geocode`로
해석하는데, OSM 없이 GTFS만 넣으면 그 엔드포인트가 404를 반환해 이름 검색이 아예
동작하지 않습니다.

## 4. 엔진 실행

준비된 파일을 확인합니다.

```
deploy/motis/
├── compose.yaml
├── config.yml
└── data/
    ├── ktdb-gtfs.zip
    └── south-korea-latest.osm.pbf
```

`config.yml`은 저장소에 포함돼 있으며 `motis config`가 만드는 기본 설정과 두 가지가
다릅니다 — 타일 블록 제거, 입력 파일명 고정. 이유는 파일 안의 주석에 적어 두었습니다.
같은 디렉터리의 [`README.md`](../deploy/motis/README.md)에는 파일별 역할이 짧게 정리돼
있습니다.

### 4-1. 그래프 빌드 (1회)

```bash
cd deploy/motis
docker compose --profile import run --rm motis-import
```

**데이터를 갱신할 때만 다시** 실행하면 되고, 서버를 켤 때마다 할 필요는 없습니다.

진행 중에는 `osr`·`tt`·`adr`·`adr_extend`·`matches` 다섯 개 태스크의 진행률 막대가
갱신됩니다. 화면이 멈춘 것처럼 보여도 `osr`은 원래 오래 걸립니다. 성공하면 다섯 줄이 모두
`100% | FINISHED`가 되고 컨테이너가 **종료 코드 0**으로 끝납니다.

성공 여부를 확실히 하려면 위 명령을 이렇게 실행하세요.

```bash
docker compose --profile import run --rm motis-import && echo "== 빌드 성공 =="
du -sh data/graph        # 1.5 GB 안팎이면 정상
```

`data/graph/`가 없거나 수십 MB에 그친다면 실패한 것입니다 —
[8절](#8-문제-해결)의 빌드 단계 항목을 보세요.

> **원본 입력을 지우기 전에 읽으세요.** 빌드가 끝나면 `ktdb-gtfs.zip`과
> `south-korea-latest.osm.pbf`를 삭제해도 서버는 동작합니다(약 500 MB 회수). 하지만
> [6절](#6-데이터의-한계)에 적었듯 **그래프는 1년치만 담으므로 언젠가 반드시 다시 빌드해야
> 하고**, 그때 GTFS는 `curl` 한 줄이 아니라 [3-1절](#3-1-대중교통-시간표-gtfs)의
> 신청 절차를 다시 밟아야 합니다. 500 MB를 아끼려다 재구축이 며칠 걸릴 수 있습니다.
> 여유가 있다면 **그냥 두는 편을 권합니다.**

### 4-2. 서버 기동

```bash
cd deploy/motis
docker compose up -d motis-server
docker compose ps        # 수동으로 다시 실행해 STATUS를 확인합니다
```

`docker compose ps`는 자동으로 갱신되지 않으니 직접 다시 실행하세요. STATUS는
`(health: starting)` → `(healthy)` 순으로 바뀝니다. **`(health: starting)`은 정상**이며,
설정상 최초 60초 동안은 계속 그렇게 보입니다. 실패가 확정되기까지는 약 2분 30초가
걸리므로, 15초쯤 보고 판단하지 마세요.

기본적으로 **`127.0.0.1:8080`에만** 바인딩됩니다. MOTIS에는 인증이 없으므로, 외부에서
접근 가능하게 만들려면 그 의미를 이해한 뒤 `compose.yaml`의 `ports`를 직접 바꾸세요.
포트를 바꿨다면 [5절](#5-naeryeo와-연결)의 `--motis-url`도 같이 바꿔야 합니다.

## 5. naeryeo와 연결

```bash
naeryeo setup --provider=motis --motis-url=http://localhost:8080 --geocoder=none
```

`--geocoder=none`은 **외부 장소 검색을 쓰지 않겠다**는 뜻입니다. 이래도 역명·건물명·도로명
주소가 모두 동작합니다 — MOTIS 색인이 셋 다 담고 있기 때문입니다([7절](#7-남는-외부-의존)).
자체 호스팅의 기본값으로 이것을 권합니다. 나중에 언제든 바꿀 수 있습니다.

마지막에 `저장하시겠습니까? [Y/n]:`이라고 한 번 묻습니다. Enter 또는 `y`면 저장합니다.
스크립트에서 돌린다면 `yes |`를 앞에 붙이세요.

또는 대화식으로:

```bash
naeryeo setup
```

이때는 제공자(자체 호스팅이 1번이자 Enter 기본값) → MOTIS 주소 → 장소 검색 사용 여부 →
저장 확인 순으로 묻습니다. 장소 검색 단계에서는 위와 같은 이유로 "사용 안 함"을 고르면
됩니다.

이 단계에서 naeryeo가 엔진에 연결하지 못하면 `엔진에 연결할 수 없습니다`, 엔진은 응답하지만
MOTIS가 아닌 것 같으면 `엔진이 요청을 거부했습니다. 주소가 MOTIS 서버가 맞는지 확인하세요`가
나옵니다. 어느 쪽이든 [4-2절](#4-2-서버-기동)로 돌아가 서버 상태와 주소를 확인하세요.

설정을 저장하기 전에 naeryeo가 엔진에 연결해 **데이터가 적재되었는지 확인**합니다. 엔진이
응답하지만 시간표·지도 데이터가 없으면 저장을 거부하고 이 문서를 안내합니다.

연결되면 상용 API 키 없이 바로 검색됩니다.

```bash
naeryeo route --from 강남역 --to 홍대입구역
```

## 6. 데이터의 한계

자체 호스팅의 결과가 상용 서비스와 다른 이유는 대부분 엔진이 아니라 **데이터**에 있습니다.

**시간표가 2023년 3월 기준입니다.** 이것이 가장 중요한 한계입니다. KTDB 공지는 이 자료를
"파일럿 자료"로 표기하고 있고 **갱신 주기를 명시하지 않습니다**. 그 사이의 노선 신설·폐지·
개편이 반영돼 있지 않습니다.

**그런데 이 노후화는 오류로 드러나지 않습니다.** 피드의 `calendar.txt`는 서비스 하나가
2030년까지 매일 운행하는 것으로 선언돼 있습니다. 따라서 엔진은 오늘 날짜 질의에 대해
"경로 없음"이 아니라 **3년 전 시각표로 계산한 결과를 정상 응답으로 돌려줍니다**. 실패보다
알아채기 어려운 형태이므로, 실제 통행에 쓰기 전에 최신 정보와 대조하세요.

**평일·주말·공휴일 구분이 없습니다.** 위와 같은 이유로 모든 요일이 동일한 시각표를
사용합니다. `calendar_dates.txt`가 없어 공휴일 예외도 없습니다.

**실시간 정보가 없습니다.** 지연·결행·우회는 반영되지 않습니다. 이 구성에는 GTFS-RT
피드가 연결돼 있지 않습니다.

**요금 정보가 없습니다.** 피드에 운임 데이터가 없어 naeryeo는 `요금 정보 없음`으로
표시하고, `--json` 출력에서는 `fareWon` 키를 아예 내보내지 않습니다.

**노선 종별이 GTFS 표준과 어긋납니다.** 피드가 시내버스를 트램(`route_type=0`)으로,
KTX·SRT를 곤돌라(`6`)로, 항공 국내선을 강삭철도(`7`)로 표기합니다. 엔진은 이 값을 그대로
믿으므로 KTX 구간이 `AERIAL_LIFT`로 보고됩니다.

naeryeo 출력에서 이것이 드러나는 지점은 하나입니다. **실제 시내버스인데 "버스"라는 말이
빠집니다** — `강남에서 6900 승차`처럼 노선 번호만 나옵니다. 피드가 그 노선을 버스로
표기하지 않았기 때문입니다. 반대로 지하철·철도는 원래도 수단 이름 없이 노선명만 쓰므로
(`강남에서 서울2호선 승차`) 달라지는 것이 없습니다. 노선명 자체는 모든 경우에 정확해
읽는 데 지장은 없습니다.

**커버리지**: 공지상 전국(도서지역 포함)이며 시내/마을버스, 도시철도, 연안해운, 시외버스,
일반철도, 공항리무진, 고속철도, 항공(국내선)을 포함합니다. 실제로 수도권 도시철도·지방
광역시 시내·도시 간 철도 세 종류를 검증했고 모두 정상 동작했습니다([9절](#9-구축-완료-판정)).

**시간표 적재 창**: 그래프는 빌드 시점부터 **약 1년치**(실측: 빌드 전날 00시부터 366일)
시간표만 담습니다. 그 창을 벗어나면 엔진이 질의를 거부하므로, **1년에 한 번 이상은 다시
빌드해야 합니다**. naeryeo에는 날짜를 지정하는 옵션이 없으니, 이 한계는 "미래 날짜를
물었을 때"가 아니라 "그래프를 오래 방치했을 때" 나타납니다.

## 7. 남는 외부 의존

자체 호스팅으로 **경로 검색의 외부 의존은 사라집니다.** 장소 이름 해석도 대부분 함께
사라집니다 — 생각보다 많이.

MOTIS의 색인은 GTFS 정류장뿐 아니라 **OSM에서 온 건물·장소·주소까지** 담습니다
([3-2절](#3-2-도로보행-네트워크-osm)의 `.osm.pbf`가 그 출처입니다). 그래서 아래가 전부
외부 호출 0건으로 동작합니다.

| 입력 | 외부 서비스 | 실측 |
| --- | --- | --- |
| 역·정류장 이름 (`강남역`) | 필요 없음 | `type=STOP`으로 해석 |
| 건물명 (`아이디스 타워`) | 필요 없음 | `type=PLACE`로 해석 |
| 도로명 주소 (`테헤란로 152`) | 필요 없음 | `type=ADDRESS`로 해석 |

위 세 가지 모두 `--geocoder=none` 상태에서 실제로 검색해 확인했습니다.

**그렇다면 Kakao 장소 검색은 무엇인가요?** MOTIS 색인에 **없는** 이름을 위한 예비 수단입니다.
naeryeo는 항상 MOTIS에게 먼저 묻고, 결과가 있으면 거기서 끝냅니다. 비어 있을 때만 — 그리고
키를 등록해 둔 경우에만 — Kakao에 다시 묻습니다. 새로 생긴 상호처럼 OSM에 아직 반영되지
않은 이름에서 차이가 납니다.

정리하면, 자체 호스팅 + `--geocoder=none`은 **어떤 외부 서비스도 호출하지 않으면서** 역명·
건물명·주소를 모두 다룹니다. Kakao를 켜는 것은 적중률을 조금 높이는 선택이지 기능을 여는
스위치가 아닙니다.

이 선택은 **경로 검색 제공자와 독립적**입니다. 자체 호스팅을 쓰면서 장소 검색만 켤 수도,
ODsay를 쓰면서 장소 검색을 끌 수도 있습니다. 나중에 바꾸려면 `naeryeo setup --geocoder=kakao`
또는 `--geocoder=none`을 실행하세요.

이 절은 [6절](#6-데이터의-한계)과 다른 이야기입니다. 6절은 데이터의 품질과 범위를,
이 절은 의존성의 축을 다룹니다.

## 8. 문제 해결

### 8-A. 빌드·기동 단계 (naeryeo가 관여하기 전)

이 단계의 실패는 아래 오류 코드로 나타나지 않습니다. 컨테이너가 죽거나 뜨지 않습니다.

**빌드가 갑자기 죽고 종료 코드가 137이다** — 메모리 부족(OOM)입니다. 컨테이너에 할당된
메모리를 8 GB로 올리세요([2-2절](#2-2-자원-요구치)). Docker Desktop은 Settings → Resources
→ Memory에서 바꿉니다.

**빌드 도중 "No space left on device"** — 디스크 부족입니다. 그래프만 1.5 GB이고 빌드 중
임시 공간이 더 필요합니다. 5 GB 이상 비우고 `data/graph`를 지운 뒤 다시 하세요.

**빌드는 성공했다는데 `data/graph`가 비었거나 아주 작다** — 입력 파일 이름이 틀렸을 수
있습니다. `deploy/motis/data/`에 정확히 `ktdb-gtfs.zip`과 `south-korea-latest.osm.pbf`가
있는지 확인하세요([3절](#3-데이터-확보)).

**`docker compose up`이 포트 바인딩 실패로 끝난다** — 8080 포트를 이미 다른 것이 쓰고
있습니다. 그것을 끄거나, `compose.yaml`의 `ports`를 `"127.0.0.1:18080:8080"` 같은 값으로
바꾸세요. 바꿨다면 [5절](#5-naeryeo와-연결)의 `--motis-url`도 같은 포트로 맞춰야 합니다.

**입력 파일이 이상하다는 오류** — 받다 만 파일일 수 있습니다.
[3절](#3-데이터-확보)의 크기 확인을 다시 하세요.

### 8-B. 검색 단계 (naeryeo 오류 코드)

naeryeo가 내는 오류 코드별로 정리했습니다. `--json`을 붙이면 코드를 직접 볼 수 있습니다.

### `provider_not_configured`

아직 제공자를 고르지 않았습니다. [5절](#5-naeryeo와-연결)의 `naeryeo setup`을 실행하세요.
업그레이드 직후라면 기존 키가 남아 있어도 이 오류가 납니다 — 설정을 한 번 다시 하면 됩니다.

### `motis_unavailable`

엔진에 연결하지 못했습니다. 연결 실패·타임아웃·5xx가 여기에 해당합니다.

```bash
cd deploy/motis
docker compose ps                     # 서버가 떠 있는지, healthy인지
docker compose logs --tail=50 motis-server
```

`(unhealthy)`로 굳어 있다면 그래프 빌드가 끝나지 않았거나 `data/graph/`가 비어 있을 수
있습니다. [4-1절](#4-1-그래프-빌드-1회)을 다시 수행하세요.

주소를 잘못 넣은 경우에도 이 코드가 납니다. `naeryeo setup --provider=motis --motis-url=...`로
다시 지정하세요.

### `motis_rejected`

엔진에 닿기는 했는데 응답이 정상이 아닙니다. 두 가지 원인이 있습니다.

**(가) 주소가 MOTIS 서버가 아닙니다.** `--motis-url`이 다른 웹 서버나 프록시를 가리키면,
연결은 되지만 돌아온 응답을 해석할 수 없어 이 코드가 납니다. 주소를 확인하세요 — 연결
자체가 거부되는 경우는 `motis_unavailable`입니다.

```bash
curl "http://localhost:8080/api/v1/geocode?text=강남역"   # MOTIS라면 JSON 배열이 나옵니다
```

**(나) 그래프가 만료됐습니다.** 그래프는 빌드 시점부터 약 1년치 시간표만 담습니다. 1년 넘게
다시 빌드하지 않았다면 오늘 날짜가 그 범위 밖이 되어 엔진이 질의를 거부합니다. 다시
빌드하세요.

```bash
cd deploy/motis
docker compose stop motis-server     # 먼저 멈춥니다 — 아래를 보세요
rm -rf data/graph
docker compose --profile import run --rm motis-import
docker compose start motis-server
```

**서버를 먼저 멈추는 것이 중요합니다.** 실행 중인 서버는 그래프 파일을 메모리에 매핑해
두고 있어서, 켜 둔 채로 지우고 새로 쓰면 서버가 반쯤 사라진 데이터를 붙들게 됩니다.

재빌드에는 원본 입력 두 개가 다시 필요합니다. 지웠다면
[3절](#3-데이터-확보)부터 다시 해야 하며, GTFS는 신청 절차를 다시 밟아야 합니다.

### `no_route`

두 지점 사이에 경로가 없습니다. 정말로 연결편이 없을 수도 있지만, **시간표 데이터가
비어 있거나 만료된 경우에도** 같은 코드가 납니다. 엔진은 운행일이 하나도 없는 시간표를
경고 없이 적재하므로, 다른 질의도 전부 `no_route`라면 GTFS 파일부터 의심하세요.

### `point_not_found`

출발지나 도착지 이름을 좌표로 바꾸지 못했습니다. `--json` 출력에는 어느 쪽인지(`side`)와
문제가 된 이름이 함께 담깁니다.

MOTIS 색인에는 역·정류장뿐 아니라 건물명·도로명 주소도 들어 있으므로([7절](#7-남는-외부-의존)),
이 오류는 대개 **그 이름이 OSM·GTFS 어디에도 없다**는 뜻입니다. 엔진에 직접 물어 확인하세요.

```bash
curl "http://localhost:8080/api/v1/geocode?text=강남역"
```

빈 배열이 나오면 표기를 바꿔 보거나(`역` 붙이기/떼기), 근처의 알려진 정류장 이름을 쓰세요.
새로 생긴 상호처럼 OSM에 아직 없는 이름이라면 Kakao 장소 검색을 켜는 것이 도움이 됩니다
(`naeryeo setup --geocoder=kakao`).

## 9. 구축 완료 판정

아래 5개가 모두 예이면 구축이 끝난 것입니다.

- [ ] **문서 바깥 지식 없이 여기까지 왔는가** — 이 문서에 없는 정보를 검색해야 했다면
      그 지점을 이슈로 남겨 주세요.
- [ ] **착수 전에 자원 요구치를 알 수 있었는가** — [2절](#2-준비물과-자원-요구치)의 실측표를
      보고 내 장비로 가능한지 판단할 수 있었어야 합니다.
- [ ] **도중에 자원 부족으로 중단되지 않았는가** — 컨테이너 메모리 8 GB, 디스크 5 GB가
      기준입니다.
- [ ] **데이터의 갱신 주기·커버리지 한계를 알고 있는가** — [6절](#6-데이터의-한계).
      특히 시간표가 2023년 3월 기준이며 그 노후화가 조용히 지나간다는 점.
- [ ] **이미지 태그와 데이터 출처가 고정돼 있는가** — 엔진은 고정돼 있습니다:
      `compose.yaml`이 `2.11.0`을 못 박고 `latest`를 쓰지 않습니다. **데이터는 고정돼 있지
      않습니다** — OSM은 매일 갱신되는 `-latest` 파일이고, GTFS에는 버전 표기도 체크섬도
      없습니다([3절](#3-데이터-확보)). 같은 그래프를 다시 만들어야 한다면 받은 원본 파일을
      직접 보관하세요.

동작 확인은 아래 세 질의로 합니다. 세 종류의 통행이 각각 커버되는지 보는 것이 목적입니다.

```bash
naeryeo route --from 강남역   --to 홍대입구역     # 수도권 도시철도
naeryeo route --from 서면역   --to 해운대역       # 지방 광역시 시내
naeryeo route --from 대전역   --to 광주송정역     # 도시 간 (KTX·SRT)
```

2026-08-03 검증에서는 각각 약 48분(환승 0회, 서울2호선), 약 33분(환승 0회, 부산2호선),
약 93~159분(환승 1회, KTX 경부선 + SRT 호남선)이 나왔습니다. **소요 시간은 질의한 시각에
따라 달라지므로** 분 단위가 다른 것은 정상입니다. 판정 기준은 "경로가 나오는가"입니다.

세 질의 모두 `요금 정보 없음`으로 끝나는 것이 정상입니다([6절](#6-데이터의-한계)).
