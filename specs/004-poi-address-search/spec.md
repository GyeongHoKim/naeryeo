# Feature Specification: 건물명·주소(POI) 출발지/도착지 지원

**Feature Branch**: `004-poi-address-search`

**Created**: 2026-07-02

**Status**: Draft

**Input**: User description: "route 검색에서 역/정류장 이름뿐 아니라 건물명·주소 같은 일반 장소(POI)도 출발지/도착지로 입력할 수 있게 한다. 현재는 ODsay searchStation(정류장 검색)만 사용해 \"아이디스 타워\" 같은 건물명은 좌표로 해석되지 않아 \"출발지를 찾을 수 없습니다\"로 실패한다. 정류장 검색으로 좌표를 얻지 못한 경우 외부 지오코더(예: Kakao Local 키워드 검색)로 폴백해 이름을 좌표로 변환한 뒤, 기존 좌표 기반 경로 검색(searchPubTransPathT)으로 이어지게 한다. 외부 지오코더는 별도 API 키가 필요하므로 사용자 setup 및 키 저장(feature 001 키체인) 흐름에 영향이 있다."

## Clarifications

### Session 2026-07-02

- Q: 장소 검색(지오코딩) API 키를 어떻게 저장할까? → A: OS 키체인에 ODsay 키와 별개의 항목으로 저장한다(feature 001 저장 메커니즘 재사용). 환경변수 주입은 이 기능 범위에서 지원하지 않는다.
- Q: 장소 검색 API 키를 등록하는 CLI 진입점은? → A: 기존 `setup`/`logout` 명령에 대상 지정 플래그(예: `--geocoder`)를 추가해 어떤 키를 등록/삭제할지 구분한다. 별도 명령이나 별도 서브커맨드는 만들지 않는다. (사용자 미응답으로 추천안 채택 — 후속 조정 가능.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 건물명·주소로 경로 검색 (Priority: P1)

사용자가 역/정류장 이름이 아닌 건물명이나 주소(예: "아이디스 타워", "판교역로 235")를 출발지 또는 도착지로 입력해도, 시스템이 그 장소를 지도상의 위치로 해석해 대중교통 경로를 검색해 준다.

**Why this priority**: 이것이 이 기능의 존재 이유다. 현재는 등록된 역/정류장 명칭만 인식되어, 사용자가 실제로 알고 있는 "출발하는 건물/도착하는 건물" 이름으로는 검색이 실패한다. 이 흐름이 없으면 사용자는 자기 위치를 가장 가까운 정류장 이름으로 직접 변환해야 하는 부담을 진다.

**Independent Test**: 정류장 이름으로는 검색되지 않지만 실제로 존재하는 건물명(예: "아이디스 타워")을 출발지로, 역명(예: "수지구청")을 도착지로 입력해 경로 검색을 호출하고, 총 소요시간·환승 횟수·요금·단계별 안내가 채워진 결과를 받는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 출발지가 등록된 정류장이 아니지만 지도상 식별 가능한 건물명이고 도착지는 유효한 지점인 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 건물명을 해당 위치로 해석해 정상적인 경로 결과(소요시간·환승·요금·단계별 안내)를 반환한다.
2. **Given** 출발지와 도착지가 모두 정류장이 아닌 건물명/주소인 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 두 장소를 각각 위치로 해석해 경로 결과를 반환한다.
3. **Given** 입력한 이름이 정류장으로도, 건물명/주소로도 유효한 상태(예: "수지구청"), **When** 경로 검색을 요청하면, **Then** 시스템은 기존과 동일하게 정류장 해석을 우선 사용해 결과를 반환한다(회귀 없음).

---

### User Story 2 - 장소 검색용 API 키 설정 (Priority: P1)

건물명·주소 해석에는 외부 장소 검색 서비스가 필요하고 이 서비스는 별도의 API 키를 요구한다. 사용자는 이 키를 한 번 등록해 두면 이후 경로 검색에서 건물명·주소 해석이 자동으로 동작한다.

**Why this priority**: User Story 1이 실제로 동작하려면 장소 검색 서비스 인증 수단이 갖춰져야 한다. 키 등록 경로가 없으면 건물명·주소 검색은 어떤 경우에도 성공할 수 없다.

**Independent Test**: 장소 검색 API 키를 등록하는 흐름을 실행해 키가 안전하게 저장되는지 확인하고, 저장된 키가 이후 건물명 검색에 사용되어 좌표 해석이 성공하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 장소 검색 서비스의 API 키를 가지고 있는 상태, **When** 설정 흐름으로 그 키를 등록하면, **Then** 시스템은 키를 안전하게 저장하고 이후 경로 검색에서 건물명·주소 해석에 사용한다.
2. **Given** 장소 검색 API 키가 이미 저장되어 있는 상태, **When** 건물명을 출발지로 경로 검색을 요청하면, **Then** 시스템은 저장된 키로 장소를 해석해 경로 결과를 반환한다.

---

### User Story 3 - 해석 실패 및 미설정에 대한 명확한 안내 (Priority: P2)

건물명·주소를 해석할 수 없거나 장소 검색 키가 설정되지 않은 경우, 사용자는 무엇이 문제인지, 어떻게 해결하는지 이해할 수 있는 안내를 받는다.

**Why this priority**: 핵심 성공 경로(User Story 1, 2)가 갖춰진 뒤 다뤄야 할 예외 처리지만, 이 안내가 없으면 사용자는 "왜 여전히 못 찾는지" 원인 불명의 실패를 반복하게 되므로 초기 릴리스에 포함되어야 한다.

**Independent Test**: (a) 장소 검색 키 미설정 상태에서 건물명을 검색해 "키 설정 필요" 안내가 나오는지, (b) 키는 설정됐으나 존재하지 않는 장소명을 검색해 "찾을 수 없음" 안내가 나오는지 각각 확인한다.

**Acceptance Scenarios**:

1. **Given** 장소 검색 API 키가 설정되지 않았고 입력한 출발지가 정류장으로도 해석되지 않는 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 정류장으로 찾을 수 없으며 건물명·주소 검색을 쓰려면 장소 검색 키 설정이 필요함을 안내한다.
2. **Given** 장소 검색 API 키는 설정됐지만 입력한 이름이 정류장으로도 장소로도 식별되지 않는 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 어느 쪽(출발지/도착지)을 해석하지 못했는지 알 수 있는 "찾을 수 없음" 안내를 반환한다.
3. **Given** 장소 검색 서비스가 일시적으로 응답하지 않거나 오류를 반환하는 상태, **When** 건물명으로 경로 검색을 요청하면, **Then** 시스템은 무한정 대기하거나 예기치 않게 종료되지 않고 원인을 설명하는 에러로 응답한다.

### Edge Cases

- 건물명/주소로 여러 후보가 반환되는 경우(동명 건물, 광범위한 지명), 시스템은 어떤 후보를 선택했는가? (기본: 검색 서비스가 반환한 최상위 후보 1건을 사용 — 기존 정류장 검색이 첫 후보를 쓰는 방식과 일관)
- 정류장 검색과 장소 검색이 서로 다른 위치를 반환할 수 있는 이름(예: 정류장 "○○입구"와 건물 "○○")의 경우, 우선순위 규칙은? (기본: 정류장 해석 우선, 실패 시에만 장소 검색으로 폴백)
- 장소 검색 키는 설정됐으나 정류장 검색만으로 이미 좌표를 얻은 경우, 불필요한 장소 검색 호출을 하지 않는가? (기본: 정류장 검색이 성공하면 장소 검색을 호출하지 않음)
- 출발지는 정류장으로, 도착지는 건물명으로 해석되는 혼합 입력을 정상 처리하는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 출발지·도착지 각각에 대해, 먼저 대중교통 정류장 검색으로 위치 해석을 시도해야 한다(기존 동작 유지).
- **FR-002**: 정류장 검색으로 위치를 얻지 못한 경우, 시스템은 외부 장소 검색(지오코딩) 서비스로 폴백해 해당 이름을 지도상의 위치로 해석해야 한다.
- **FR-003**: 시스템은 정류장 검색으로 위치를 얻은 경우에는 장소 검색 서비스를 호출하지 않아야 한다(불필요한 외부 호출 방지).
- **FR-004**: 장소 검색 서비스가 하나의 이름에 대해 여러 후보를 반환하면, 시스템은 서비스가 제공한 최상위(대표) 후보 1건의 위치를 사용해야 한다.
- **FR-005**: 사용자는 설정 흐름을 통해 장소 검색 서비스의 API 키를 등록할 수 있어야 하며, 시스템은 이 키를 OS 키체인에 ODsay 키와 동일한 수준·별개 항목으로 안전하게 저장해야 한다(환경변수 주입은 지원하지 않음).
- **FR-006**: 시스템은 장소 검색용 API 키를 대중교통 경로 검색용 API 키와 별개의 항목으로 관리해야 한다(서로 독립적으로 등록·조회·삭제 가능).
- **FR-006a**: 사용자는 기존 `setup`/`logout` 명령에 대상 지정 플래그(예: `--geocoder`)를 붙여 장소 검색 키를 등록·삭제할 수 있어야 한다. 플래그가 없으면 기존과 동일하게 대중교통 경로 검색용 키를 대상으로 한다.
- **FR-007**: 장소 검색 API 키가 설정되지 않은 상태에서 정류장으로도 해석되지 않는 이름을 입력하면, 시스템은 "정류장으로 찾을 수 없으며 건물명·주소 검색에는 장소 검색 키 설정이 필요하다"는 취지의 안내를 반환해야 한다.
- **FR-008**: 정류장·장소 검색 모두로 이름을 식별하지 못한 경우, 시스템은 어느 쪽(출발지/도착지)을 해석하지 못했는지 구분되는 "찾을 수 없음" 안내를 반환해야 한다.
- **FR-009**: 장소 검색 서비스가 응답 지연·오류·인증 실패를 반환하는 경우, 시스템은 무한정 대기하지 않고 원인을 설명하는 에러로 응답해야 하며, 이를 "장소를 찾을 수 없음"과 구분해야 한다.
- **FR-010**: 위치 해석 이후의 경로 검색·결과 표현(소요시간·환승·요금·단계별 안내)은 기존 동작을 그대로 따라야 한다. 이 기능은 이름→위치 해석 단계만 확장한다.
- **FR-011**: 이 기능은 CLI(`route`)와 MCP 두 진입점에서 동일하게 동작해야 한다(공유 코어 로직 확장).
- **FR-012**: 장소 검색 폴백 기능은 장소 검색 키가 없어도 기존 정류장 기반 검색이 계속 정상 동작하도록, 선택적(opt-in) 확장으로 동작해야 한다.

### Key Entities *(include if feature involves data)*

- **장소 검색 API 키**: 외부 장소 검색(지오코딩) 서비스에 대한 사용자별 인증 자격 증명. 대중교통 경로 검색용 API 키와는 별개의 저장 항목으로 관리된다.
- **해석된 위치(Resolved Location)**: 이름(정류장명/건물명/주소)을 지도상의 좌표로 변환한 결과. 해석 출처(정류장 검색 / 장소 검색)를 구분할 수 있어야 진단·안내에 활용된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 정류장으로 등록되지 않은 대표 건물명(예: "아이디스 타워")을 출발지로 입력한 경로 검색이, 장소 검색 키가 설정된 상태에서 정상적인 경로 결과를 반환한다(현재는 100% 실패).
- **SC-002**: 기존에 정류장 이름만으로 성공하던 경로 검색은 이 기능 도입 후에도 동일하게 성공한다(회귀 0건).
- **SC-003**: 정류장으로 해석 가능한 입력에 대해서는 장소 검색 서비스 호출이 발생하지 않는다(불필요한 외부 호출 0건).
- **SC-004**: 건물명·주소 해석 실패, 장소 검색 키 미설정, 서비스 오류의 세 가지 상황이 사용자에게 서로 구분되는 안내로 전달되어, 사용자가 다음 조치(키 설정/입력 수정/재시도)를 판단할 수 있다.

## Assumptions

- **정류장 우선, 장소 검색은 폴백**: 이름은 먼저 정류장 검색으로 해석하고, 실패한 경우에만 장소 검색으로 폴백한다. 이는 기존 동작과의 하위 호환을 보장하고, 대중교통 명칭에 대해서는 가장 정확한 해석을 유지하기 위함이다.
- **대표 후보 1건 사용**: 장소 검색이 여러 후보를 반환해도 대표(최상위) 1건을 사용한다. 후보 목록을 사용자에게 제시해 고르게 하는 상호작용은 이 기능의 범위 밖이며, 필요 시 후속 기능으로 다룬다.
- **장소 검색 키는 선택적**: 장소 검색 키가 없는 사용자도 기존 정류장 기반 검색을 그대로 사용할 수 있다. 이 기능은 그 위에 얹히는 opt-in 확장이다.
- **키 저장 방식**: 장소 검색 API 키는 대중교통 API 키와 동일하게 OS 키체인(feature 001의 저장 메커니즘)에 별도 항목으로 저장한다(Clarifications 2026-07-02에서 확정). 환경변수 주입은 이 기능 범위에서 지원하지 않는다.
- **외부 장소 검색 서비스**: 한국 건물명·주소·POI 해석을 지원하는 외부 지오코딩 서비스를 사용한다(구체 서비스·엔드포인트 선정은 계획 단계 `/speckit-plan`의 조사 대상). ODsay 자체에는 건물명·주소 지오코딩 엔드포인트가 없음이 확인되었다.
- **범위 경계**: 위치 해석(이름→좌표) 단계만 확장하며, 좌표 기반 경로 검색·결과 포맷팅·CLI 플래그 파싱·MCP 프로토콜 처리는 기존 기능(002/003)의 동작을 그대로 재사용한다.
