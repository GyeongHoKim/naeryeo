# Feature Specification: 대중교통 경로 검색 (ODsay 연동 코어 로직)

**Feature Branch**: `002-odsay-route-search`

**Created**: 2026-07-01

**Status**: Draft

**Input**: User description: "ODsay API를 감싸는 internal/core 패키지: 사용자가 출발지와 도착지(역/정류장 이름 또는 주소)를 입력하면 대중교통(버스/지하철/시외버스) 경로를 검색해 사람이 읽을 수 있는 형태로 반환한다. CLI의 `naeryeo route --from <출발지> --to <도착지>` 명령과 MCP 서버가 공통으로 사용하는 핵심 로직이다. 결과에는 총 소요시간, 환승 횟수, 단계별 경로 안내(예: \"강남역에서 2호선 승차\", \"신도림역에서 환승\"), 요금이 포함되어야 한다. API 키는 internal/config에서 조회하며, 키가 설정되어 있지 않으면 사용자에게 `naeryeo setup`을 먼저 실행하라고 안내해야 한다. 출발지/도착지를 ODsay가 인식하지 못하거나 경로가 없는 경우, 사용자가 이해할 수 있는 에러 메시지를 반환해야 한다. 이 기능은 route/mcp 두 진입점이 공유하는 순수 라우팅 로직이며, 실제 CLI 플래그 파싱이나 MCP 프로토콜 처리는 이 기능의 범위 밖이다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 출발지·도착지로 대중교통 경로 검색 (Priority: P1)

사용자가 출발지와 도착지 명칭을 입력하면, 대중교통(지하철·버스·시외버스)을 이용한 경로를 검색해 총 소요시간, 환승 횟수, 요금, 그리고 사람이 이해할 수 있는 단계별 이동 안내를 받는다.

**Why this priority**: 이것이 naeryeo의 핵심 가치 그 자체다. 이 흐름 없이는 CLI든 MCP든 어떤 진입점도 제품으로서 의미가 없다.

**Independent Test**: 실제로 대중교통으로 연결된 두 지점(예: "강남역", "홍대입구역")을 입력해 검색 함수를 직접 호출하고, 반환된 결과에 소요시간·환승 횟수·요금·단계별 안내가 모두 채워져 있는지 확인하는 것만으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 유효한 API 키가 설정되어 있고 출발지·도착지가 모두 실제 존재하는 지점인 상태, **When** 두 지점 이름으로 경로 검색을 요청하면, **Then** 총 소요시간, 환승 횟수, 요금, 단계별 이동 안내(예: "강남역에서 2호선 승차", "신도림역에서 환승")가 모두 포함된 결과를 받는다.
2. **Given** 출발지와 도착지 사이에 환승 없이 갈 수 있는 경로가 있는 상태, **When** 경로 검색을 요청하면, **Then** 환승 횟수가 0으로 표시된 결과를 받는다.
3. **Given** 출발지와 도착지가 동일한 지점인 상태, **When** 경로 검색을 요청하면, **Then** 이동이 필요 없음을 알리는 명확한 안내를 받는다(오류로 취급되지 않음).

---

### User Story 2 - API 키 미설정 시 안내 (Priority: P1)

API 키가 아직 설정되지 않은 사용자가 경로 검색을 시도하면, 외부 서비스 호출을 시도하기 전에 먼저 `naeryeo setup`을 실행하라는 명확한 안내를 받는다.

**Why this priority**: 이 안내가 없으면 사용자는 이해할 수 없는 인증 에러를 마주하게 되어 첫 사용 경험이 크게 나빠진다. User Story 1과 마찬가지로 실제 서비스 착수 전 반드시 있어야 하는 진입 장벽 처리다.

**Independent Test**: API 키가 저장되지 않은 상태에서 임의의 출발지·도착지로 경로 검색을 호출해, 외부 서비스 호출 없이 "setup 필요" 안내가 즉시 반환되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** API 키가 저장되어 있지 않은 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 외부 경로 검색을 시도하지 않고 `naeryeo setup`을 먼저 실행하라는 안내를 반환한다.
2. **Given** 저장된 API 키가 유효하지 않아 외부 서비스 인증에 실패하는 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 이를 "키 미설정"과는 구분되는, 키가 유효하지 않다는 안내로 응답한다.

---

### User Story 3 - 인식할 수 없는 지점·경로 없음에 대한 명확한 안내 (Priority: P2)

사용자가 오타가 있거나 존재하지 않는 지점을 입력했거나, 두 지점 사이에 대중교통으로 연결되는 경로 자체가 없는 경우, 무엇이 문제인지 이해할 수 있는 에러 메시지를 받는다.

**Why this priority**: 핵심 성공 경로(User Story 1)가 갖춰진 뒤에 다뤄야 할 예외 처리이지만, 이 안내가 없으면 사용자가 원인 불명의 실패를 반복해서 겪게 되므로 초기 릴리스에 포함되어야 한다.

**Independent Test**: 존재하지 않는 지점 이름과, 실제 존재하지만 대중교통으로 연결되지 않는 두 지점 이름 각각으로 검색을 요청해, 서로 구분되는 명확한 에러 메시지를 받는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 출발지 또는 도착지 이름이 실제 존재하는 지점과 일치하지 않는 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 어떤 지점(출발지/도착지)을 인식하지 못했는지 알 수 있는 에러 메시지를 반환한다.
2. **Given** 출발지와 도착지 모두 유효한 지점이지만 대중교통으로 연결되는 경로가 없는 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 "경로 없음"임을 명확히 알리는 에러 메시지를 반환한다.
3. **Given** 외부 경로 검색 서비스가 일시적으로 응답하지 않거나 오류를 반환하는 상태, **When** 경로 검색을 요청하면, **Then** 시스템은 무한정 대기하거나 예기치 않게 종료되지 않고 원인을 설명하는 에러로 응답한다.

### Edge Cases

- 동일한 이름을 가진 지점이 여러 곳에 존재하는 경우(동명 정류장/역), 시스템은 어떤 후보를 선택했는지 또는 특정할 수 없음을 어떻게 알리는가?
- 출발지·도착지 중 하나가 빈 문자열로 주어지는 경우는 어떻게 처리하는가?
- 외부 경로 검색 서비스의 응답이 비정상적으로 느린 경우, 사용자는 얼마나 기다리게 되는가?
- 도보로만 이동 가능할 만큼 두 지점이 가까운 경우, 시스템은 이를 "경로 없음"과 구분해서 안내하는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 출발지와 도착지 명칭(역/정류장 이름 또는 주소)을 입력받아 대중교통 경로를 검색해야 한다.
- **FR-002**: 시스템은 지하철, 버스(시내/마을), 시외버스를 포함한 대중교통 수단을 이용하는 경로를 검색 대상에 포함해야 한다.
- **FR-003**: 검색 결과는 총 소요시간을 포함해야 한다.
- **FR-004**: 검색 결과는 환승 횟수를 포함해야 한다.
- **FR-005**: 검색 결과는 사람이 읽을 수 있는 단계별 이동 안내(예: 어느 역/정류장에서 몇 호선·몇 번 버스를 승차하는지, 어디서 환승하는지, 어디서 하차하는지)를 포함해야 한다.
- **FR-006**: 검색 결과는 예상 요금을 포함해야 한다.
- **FR-007**: API 키가 설정되어 있지 않은 상태에서 검색이 요청되면, 시스템은 외부 서비스 호출을 시도하지 않고 `naeryeo setup` 실행을 안내하는 응답을 반환해야 한다.
- **FR-008**: 저장된 API 키가 유효하지 않아 외부 서비스 인증이 실패하는 경우, 시스템은 이를 "키 미설정"(FR-007)과 구분되는 에러로 알려야 한다.
- **FR-009**: 출발지 또는 도착지 명칭을 인식할 수 없는 경우, 시스템은 어느 쪽(출발지/도착지)을 인식하지 못했는지 알 수 있는 에러 메시지를 반환해야 한다.
- **FR-010**: 출발지와 도착지 사이에 대중교통 경로가 존재하지 않는 경우, 시스템은 "경로 없음"을 명확히 알리는 에러 메시지를 반환해야 한다.
- **FR-011**: 외부 경로 검색 서비스 호출이 실패(네트워크 오류, 서비스 장애, 타임아웃 등)하는 경우, 시스템은 무한정 대기하거나 예기치 않게 종료되지 않고 원인을 설명하는 에러로 응답해야 한다.
- **FR-012**: 출발지와 도착지가 동일한 지점으로 주어지는 경우, 시스템은 이를 오류가 아니라 "이동 불필요"로 안내해야 한다.
- **FR-013**: 시스템은 이 경로 검색 로직을 CLI(`route`)와 MCP 서버 양쪽이 동일하게 재사용할 수 있는 형태로 제공해야 한다. CLI 플래그 파싱과 MCP 프로토콜 처리 자체는 이 기능의 책임이 아니다.
- **FR-014**: 동일한 출발지·도착지 쌍에 대해 여러 경로 후보가 존재하는 경우, 시스템은 그중 대표 경로 하나를 선택해 반환해야 한다.

### Key Entities

- **경로 검색 질의(RouteQuery)**: 사용자가 입력한 출발지 명칭과 도착지 명칭으로 구성된다.
- **경로 검색 결과(RouteResult)**: 하나의 대표 경로에 대한 총 소요시간, 총 환승 횟수, 예상 요금, 그리고 순서가 있는 이동 단계 목록으로 구성된다.
- **이동 단계(RouteStep)**: 하나의 이동 구간에 대한 설명(예: 어느 지점에서 어떤 수단·노선으로 승차/환승/하차하는지)으로 구성되며, 여러 이동 단계가 순서대로 모여 하나의 경로 검색 결과를 이룬다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 실제로 대중교통으로 연결된 두 지점에 대한 요청의 95%는 10초 이내에 소요시간·환승 횟수·요금·단계별 안내가 모두 포함된 결과로 응답된다(외부 경로 검색 서비스가 정상 응답하는 경우 기준).
- **SC-002**: API 키가 설정되지 않은 상태에서의 요청 100%는 외부 서비스 호출 없이 즉시 setup 안내로 응답된다.
- **SC-003**: 인식할 수 없는 지점이 포함된 요청의 100%는 어떤 지점이 문제인지 알 수 있는 에러로 응답되며, 원인 불명의 실패나 시스템 크래시로 이어지지 않는다.
- **SC-004**: 경로가 존재하지 않는 요청의 100%는 "경로 없음"임을 명확히 알리는 에러로 응답된다.
- **SC-005**: 동일한 출발지·도착지 입력에 대해 CLI(`route`)와 MCP 서버 양쪽에서 항상 동일한 경로 검색 결과를 얻는다(핵심 로직이 두 진입점 사이에서 일관됨).

## Assumptions

- 검색 결과는 여러 경로 후보 중 가장 적절한(추천되는) 대표 경로 하나만 반환하는 것으로 범위를 한정한다. 여러 후보를 나열해 사용자가 선택하게 하는 기능은 이 범위 밖이다.
- 출발지·도착지는 위도/경도 좌표가 아니라 역/정류장 이름 또는 주소 같은 텍스트 명칭으로 주어지는 것을 전제로 한다(README의 사용 예시와 일치).
- 대중교통 수단은 지하철·버스(시내/마을)·시외버스로 한정하며, 택시나 도보 전용 경로 안내는 이 기능 범위 밖으로 가정한다.
- 검색 대상은 대한민국 국내 대중교통으로 한정하며, 해외 지점에 대한 검색은 지원 범위 밖으로 가정한다.
- API 키의 저장·조회·삭제 자체는 별도 기능([[001-keychain-api-key]])의 책임이며, 이 기능은 이미 저장된 키를 조회해 사용하는 소비자 입장에서만 다룬다.
- 실시간 배차 정보, 혼잡도, 좌석 여유 등 부가 정보는 README에 언급되지 않았으므로 이 기능 범위 밖으로 가정한다.
