# Feature Specification: API 키 OS 키체인 저장/조회/삭제

**Feature Branch**: `001-keychain-api-key`

**Created**: 2026-07-01

**Status**: Draft

**Input**: User description: "OS 키체인(macOS Keychain / Windows Credential Manager / Linux Secret Service)을 이용해 ODsay API 키를 저장/조회/삭제하는 internal/config 패키지. `naeryeo setup` 명령으로 API 키를 입력받아 키체인에 저장하고, `naeryeo logout` 명령으로 저장된 키를 삭제한다. go-keyring 라이브러리를 사용하며, 키체인 백엔드를 사용할 수 없는 환경(headless Linux 등 Secret Service 미존재)에서는 평문 파일 폴백 없이 에러를 반환하고 동작을 거부해야 한다. API 키는 외부로 전송되지 않으며 평문 파일에 저장되지 않는다. 이 기능은 CLI의 setup/logout 서브커맨드와, route/mcp 등 다른 기능이 저장된 키를 조회할 때 사용하는 기반 패키지다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - API 키 최초 등록 (Priority: P1)

사용자가 ODsay에서 발급받은 API 키를 `naeryeo setup` 명령으로 입력하면, 이 키가 OS의 보안 저장소(키체인)에 저장되어 이후 다른 명령에서 재입력 없이 재사용된다.

**Why this priority**: API 키 저장 없이는 `route`나 `mcp` 등 다른 모든 기능이 동작할 수 없다. 이 저장소가 없으면 제품 전체가 무의미하므로 가장 먼저 필요한 기능이다.

**Independent Test**: `naeryeo setup`을 실행해 임의의 키 문자열을 입력한 뒤, 별도 조회 절차(내부 API 또는 재실행)로 동일한 값이 반환되는지 확인하는 것만으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 키가 저장되어 있지 않은 상태, **When** 사용자가 `naeryeo setup`을 실행하고 유효한 API 키 문자열을 입력하면, **Then** 해당 키가 OS 키체인에 저장되고 성공 메시지가 표시된다.
2. **Given** 이미 키가 저장되어 있는 상태, **When** 사용자가 `naeryeo setup`을 다시 실행하고 새로운 키를 입력하면, **Then** 기존 키는 새 키로 덮어써지고 이후 조회 시 새 키만 반환된다.
3. **Given** 사용자가 setup 중 빈 문자열을 입력한 상태, **When** 저장을 시도하면, **Then** 시스템은 저장을 거부하고 유효하지 않은 입력임을 알린다.

---

### User Story 2 - 저장된 키 조회 (다른 기능의 기반) (Priority: P1)

`route`, `mcp` 등 다른 명령이 ODsay API를 호출하기 전에, 이전에 저장된 API 키를 키체인에서 조회할 수 있어야 한다.

**Why this priority**: setup으로 저장만 되고 조회할 방법이 없으면 다른 어떤 기능도 이 저장소를 활용할 수 없다. 저장과 조회는 함께 있어야 최소 기능 단위가 완성된다.

**Independent Test**: 키가 저장된 상태와 저장되지 않은 상태 각각에서 조회를 호출해, 저장된 경우 정확한 값을, 저장되지 않은 경우 "키 없음" 상태를 구분해서 받는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 키가 저장되어 있는 상태, **When** 다른 구성요소가 키 조회를 요청하면, **Then** 저장된 키 값이 정확히 반환된다.
2. **Given** 키가 저장되어 있지 않은 상태, **When** 다른 구성요소가 키 조회를 요청하면, **Then** "키 없음"이 명확히 구분되는 상태로 반환되며 임의의 다른 오류와 혼동되지 않는다.

---

### User Story 3 - 저장된 키 삭제 (Priority: P2)

사용자가 더 이상 이 도구를 사용하지 않거나 키를 교체하고 싶을 때 `naeryeo logout`으로 키체인에 저장된 API 키를 완전히 제거할 수 있다.

**Why this priority**: 보안/개인정보 관점에서 중요하지만, 저장·조회 기능(P1)이 먼저 갖춰져야 의미가 있는 부가 기능이다.

**Independent Test**: 키가 저장된 상태에서 `naeryeo logout`을 실행한 뒤, 조회 시 "키 없음" 상태가 반환되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 키가 저장되어 있는 상태, **When** 사용자가 `naeryeo logout`을 실행하면, **Then** 키체인에서 키가 삭제되고 삭제 완료 메시지가 표시된다.
2. **Given** 키가 저장되어 있지 않은 상태, **When** 사용자가 `naeryeo logout`을 실행하면, **Then** 시스템은 오류로 취급하지 않고 "삭제할 키가 없음"을 안내한다.

---

### User Story 4 - 키체인을 사용할 수 없는 환경에서의 안전한 실패 (Priority: P2)

Secret Service가 없는 headless Linux 등 OS 키체인 백엔드 자체를 사용할 수 없는 환경에서, 사용자가 `naeryeo setup`을 실행하면 평문 파일 등으로 대체 저장하지 않고 명확한 에러와 함께 동작을 거부한다.

**Why this priority**: 핵심 보안 요구사항(API 키를 평문으로 남기지 않음)을 지키기 위한 안전장치다. 지원 환경에서의 정상 동작(P1)이 먼저 확립된 뒤 검증 가능한 예외 경로다.

**Independent Test**: 키체인 백엔드가 없는 환경(또는 이를 흉내 낸 상태)에서 `naeryeo setup`을 실행해, 성공 없이 에러로 종료되고 어떤 파일에도 키가 기록되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** OS 키체인 백엔드를 사용할 수 없는 환경, **When** 사용자가 `naeryeo setup`을 실행하면, **Then** 시스템은 저장을 시도하지 않거나 실패로 처리하고, 원인을 설명하는 에러 메시지를 표시하며 0이 아닌 종료 코드로 종료한다.
2. **Given** OS 키체인 백엔드를 사용할 수 없는 환경, **When** setup이 실패한 뒤 파일시스템을 검사하면, **Then** API 키가 담긴 어떤 평문 파일도 생성되어 있지 않다.

### Edge Cases

- 키체인 접근 권한이 사용자에 의해 거부된 경우(OS 팝업에서 "거부" 선택 등), 시스템은 이를 "백엔드 사용 불가"와 동일하게 명확한 에러로 처리해야 한다.
- 키체인 백엔드가 일시적으로 잠겨 있거나(macOS Keychain 잠금) 접근 불가능한 경우, 저장/조회/삭제 요청은 실패로 처리되고 원인이 사용자에게 전달되어야 한다.
- 동일한 API 키를 이미 저장된 값과 동일하게 다시 저장하는 경우에도 정상적으로 덮어쓰기(성공)로 처리되어야 한다.
- 매우 긴 문자열이나 제어 문자가 포함된 입력값이 API 키로 주어질 경우에도 저장/조회 왕복(round-trip) 시 값이 손상되지 않아야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 `setup` 동작을 통해 ODsay API 키 문자열을 입력하면 이를 OS 키체인에 저장해야 한다.
- **FR-002**: 시스템은 다른 구성요소(`route`, `mcp` 등)가 저장된 API 키를 조회할 수 있는 방법을 제공해야 한다.
- **FR-003**: 시스템은 `logout` 동작을 통해 키체인에 저장된 API 키를 삭제할 수 있어야 한다.
- **FR-004**: 시스템은 어떤 경우에도 API 키를 평문 파일에 저장해서는 안 된다.
- **FR-005**: 시스템은 저장/조회/삭제 동작 과정에서 API 키를 외부 네트워크로 전송해서는 안 된다.
- **FR-006**: OS 키체인 백엔드를 사용할 수 없는 환경에서 시스템은 저장 동작을 명확한 에러와 함께 거부해야 하며, 평문 파일 등 다른 저장 방식으로 대체(폴백)해서는 안 된다.
- **FR-007**: 시스템은 키가 저장되어 있지 않은 상태의 조회 결과를, 그 외의 조회 실패(백엔드 오류 등)와 구분되는 상태로 반환해야 한다.
- **FR-008**: 시스템은 이미 키가 저장된 상태에서의 재저장(setup 재실행)을 기존 값에 대한 덮어쓰기로 처리해야 한다.
- **FR-009**: 시스템은 저장된 키가 없는 상태에서의 삭제(logout) 요청을 오류로 취급하지 않고, 삭제할 대상이 없음을 사용자에게 알려야 한다.
- **FR-010**: 시스템은 빈 문자열 입력을 유효한 API 키로 저장하지 않아야 한다.

### Key Entities

- **API 키(Credential)**: 사용자가 ODsay로부터 발급받은 단일 비밀 문자열. 사용자(로컬 OS 계정)당 하나만 존재하며, 저장 위치를 식별하는 고정된 서비스 식별자와 비밀 값 자체로 구성된다. 별도의 메타데이터(만료일, 다중 프로필 등)는 이 범위에 포함되지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 지원 환경(macOS/Windows/Secret Service가 있는 Linux)에서 사용자는 `setup`을 1회 실행한 뒤, 별도의 설정 파일을 만들거나 편집하지 않고도 이후 모든 명령에서 저장된 키를 재사용할 수 있다.
- **SC-002**: `setup` 성공 이후 사용자의 파일시스템을 전수 검사해도 API 키 값이 포함된 평문 파일이 100% 발견되지 않는다.
- **SC-003**: 키체인 백엔드를 사용할 수 없는 환경에서 이루어진 `setup` 시도의 100%가 성공 없이 명확한 에러 메시지로 종료되며, 이 중 어떤 시도도 평문 파일을 생성하지 않는다.
- **SC-004**: `logout` 실행 직후 이루어진 조회는 100% "키 없음" 상태로 확인된다.
- **SC-005**: 저장된 키를 조회하는 다른 기능(`route`, `mcp`)은 키 값을 있는 그대로, 즉 저장 시점과 100% 동일하게 돌려받는다(왕복 무결성).

## Assumptions

- 사용자(로컬 OS 계정)당 단일 ODsay API 키만 저장하는 것으로 범위를 한정한다. 여러 키/프로필을 전환하는 기능은 이 기능의 범위 밖이다.
- 키체인 내 저장 위치를 구분하는 서비스 식별자는 프로젝트명("naeryeo")으로 고정되어 있다고 가정한다.
- Linux 환경에서는 Secret Service(D-Bus 기반) 백엔드가 있는 데스크톱 환경을 지원 대상으로 하며, 이것이 없는 순수 headless 환경은 "키체인 사용 불가" 경로로 처리되는 것을 정상 동작으로 간주한다.
- OS별 키체인(macOS Keychain / Windows Credential Manager / Linux Secret Service)에 대한 실제 연동은 이미 검증된 외부 라이브러리(OS 키체인 연동 계층)에 위임하며, 이 기능의 책임은 그 위에서 저장/조회/삭제·에러 처리 정책을 올바르게 구성하는 데 있다.
- `setup` 재실행 시 사용자에게 별도의 덮어쓰기 확인 프롬프트 없이 조용히 덮어쓰는 것을 기본 동작으로 가정한다(일반적인 CLI 설정 도구 관례).
- 이 기능은 CLI의 `setup`/`logout` 서브커맨드 자체의 UX(프롬프트 문구 등)를 포함하되, `route`/`mcp` 명령의 나머지 로직(경로 검색, MCP 프로토콜 처리)은 별도 기능 범위로 다룬다.
