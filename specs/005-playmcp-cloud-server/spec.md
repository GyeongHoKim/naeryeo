# Feature Specification: PlayMCP Cloud MCP Server (원격 Streamable HTTP 트랙)

**Feature Branch**: `005-playmcp-cloud-server`

**Created**: 2026-07-03

**Status**: Draft

**Input**: User description: "PlayMCP(카카오 Agentic Player 10 공모전) 제출용 클라우드 MCP 서버 트랙 추가. 기존 naeryeo는 로컬 stdio MCP + CLI(ODsay BYOK)인데, 공모전은 카카오 클라우드(PlayMCP in KC)에 원격 배포하는 Streamable HTTP MCP 서버를 요구한다. 클라우드 모드에서는 ODsay를 약관상 사용할 수 없으므로 자체 호스팅 MOTIS 라우팅 백엔드를 사용하고, 라우팅 provider 인터페이스로 ODsay(로컬)와 MOTIS(클라우드)를 분리한다. PlayMCP 개발가이드(툴 annotations, 명칭 제약, p99 3s, 정제된 마크다운 결과)를 준수하고, KC Git 소스 빌드용 Dockerfile을 제공한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - PlayMCP 사용자의 자연어 경로 질의 (Priority: P1)

PlayMCP(카카오 AI 채팅)에 naeryeo 도구를 추가한 사용자가 "강남역에서 홍대입구역까지 어떻게 가?"라고 물으면, AI가 naeryeo의 경로 검색 도구를 호출하고 사용자는 소요 시간·환승 횟수·구간별 안내가 담긴 읽기 쉬운 경로 답변을 받는다. 이 흐름은 사용자가 어떤 API 키도 준비할 필요 없이 동작한다.

**Why this priority**: 공모전 제출물의 핵심 가치 그 자체. 이 시나리오가 동작하지 않으면 심사 등록조차 불가능하다.

**Independent Test**: 원격 MCP 서버를 기동하고 MCP 클라이언트(MCP Inspector 또는 PlayMCP AI 채팅)로 경로 검색 도구를 호출해, 실제 대중교통 경로가 정제된 텍스트로 반환되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 원격 MCP 서버가 기동되어 있고 라우팅 백엔드가 정상일 때, **When** 사용자가 출발지 "강남역", 도착지 "홍대입구역"으로 경로 검색 도구를 호출하면, **Then** 소요 시간, 환승 횟수, 구간별(도보/지하철/버스) 안내가 포함된 마크다운 형식의 경로 안내가 반환된다.
2. **Given** 동일 조건에서, **When** 존재하지 않는 장소명("asdfqwer역")으로 호출하면, **Then** 장소를 찾을 수 없다는 명확한 한국어 안내가 반환되고 서버 내부 정보는 노출되지 않는다.
3. **Given** 동일 조건에서, **When** 경로가 존재하지 않는 조합(예: 도보권 밖 도서 지역)으로 호출하면, **Then** "경로를 찾을 수 없음"이 정중한 문구로 반환된다.

---

### User Story 2 - 장소명 해석 (역·정류장·건물명 → 위치) (Priority: P2)

사용자는 정확한 역 이름뿐 아니라 다양한 표기("홍대입구", "강남", "서울시청")로 장소를 말한다. 시스템은 이름을 위치로 해석해 경로 검색에 사용하고, 여러 후보가 있으면 가장 그럴듯한 것을 선택한다.

**Why this priority**: 자연어 질의의 현실적 전제 조건. P1이 "정확한 역명"으로 동작한 뒤, 표기 다양성을 흡수해야 실사용이 가능해진다.

**Independent Test**: 장소명 목록(정식 역명, 축약형, 랜드마크)을 넣어 각각 위치로 해석되는지, 해석 실패 시 안내가 반환되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 서버가 정상일 때, **When** "강남"처럼 축약된 장소명으로 경로를 요청하면, **Then** 해당 이름에 대한 합리적인 위치 해석을 거쳐 경로가 반환된다.
2. **Given** 서버가 정상일 때, **When** 해석 불가능한 장소명이 입력되면, **Then** 어떤 장소를 인식하지 못했는지 명시한 안내가 반환된다.

---

### User Story 3 - 심사·운영 관점의 안정 구동 (Priority: P3)

PlayMCP 심사자(및 플랫폼)가 서버 정보를 불러오고("정보 불러오기"), 도구 메타데이터를 검증하며, 반복 호출 시에도 일관된 응답 시간과 명확한 실패 동작을 확인한다. 기존 로컬 CLI/stdio 사용자는 아무 변화도 겪지 않는다.

**Why this priority**: 심사 통과의 필요조건이지만 P1·P2가 갖춰진 뒤에 의미가 있는 요건.

**Independent Test**: MCP Inspector로 서버 스펙 준수(도구 메타데이터 포함)를 점검하고, 라우팅 백엔드를 중단시킨 상태의 실패 응답과 응답 시간 상한을 확인하며, 기존 stdio 모드 테스트가 전부 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 서버가 기동된 상태에서, **When** MCP 클라이언트가 도구 목록을 조회하면, **Then** 모든 도구에 이름·설명·입력 스키마·행동 힌트(annotations) 메타데이터가 완비되어 반환된다.
2. **Given** 라우팅 백엔드가 응답하지 않을 때, **When** 경로 검색 도구를 호출하면, **Then** 제한 시간 안에 사용자 친화적 오류 안내가 반환되고 서버는 계속 살아 있다.
3. **Given** 이 기능이 모두 구현된 상태에서, **When** 기존 로컬 stdio MCP·CLI 테스트를 실행하면, **Then** 전부 통과한다(회귀 없음).

---

### Edge Cases

- 라우팅 백엔드 지연·중단: 응답 예산(3초) 안에 타임아웃 처리 후 안내 반환. 서버 프로세스는 영향 없음.
- 장소명 해석 실패 / 다중 후보: 실패 시 인식 불가 장소를 명시, 다중 후보 시 최상위 후보 사용.
- 경로 없음(심야 시간대, 도서 지역, 동일 출발·도착): 빈 결과를 정중한 문구로 안내.
- 입력 검증: 빈 문자열, 과도하게 긴 입력, 제어 문자 등은 도구 호출 오류로 정리해 반환.
- 동시 호출: 상태를 공유하지 않는 처리(stateless)로 동시 요청 간 간섭 없음.
- 플랫폼의 서버 정보 조회("정보 불러오기")가 도구 메타데이터 불비로 실패하는 경우가 없어야 함.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 원격 접속 가능한 Streamable HTTP 방식의 MCP 서버 모드를 제공해야 한다. 세션 상태를 요구하지 않아야 하며(stateless), MCP 프로토콜 버전 2025-03-26 이상 2025-11-25 이하와 호환되어야 한다.
- **FR-002**: 원격 모드는 기존 로컬 stdio MCP·CLI와 동일한 핵심 경로 검색 흐름을 공유해야 하며, 기존 모드의 동작·테스트에 회귀가 없어야 한다.
- **FR-003**: 경로 검색은 교체 가능한 라우팅 제공자(provider) 계약 뒤에서 수행되어야 한다. 로컬 모드는 기존 ODsay 제공자를, 원격 모드는 자체 호스팅 MOTIS 백엔드 제공자를 사용한다. 원격 모드에서 ODsay가 호출되는 일이 없어야 한다(약관 준수).
- **FR-004**: MOTIS 백엔드의 접속 주소는 배포 환경에서 환경 변수로 주입되어야 하며, 미설정 시 원격 모드는 기동 시점에 명확한 오류로 실패해야 한다.
- **FR-005**: 사용자가 입력한 장소명(역·정류장·랜드마크)은 위치로 해석되어야 한다. 해석은 원격 모드에서 외부 상용 API 키 없이 동작해야 한다.
- **FR-006**: 경로 검색 도구는 PlayMCP 개발가이드를 준수해야 한다: 도구 이름은 `[A-Za-z0-9_-]` 1~128자, 어떤 위치에도 "kakao" 문자열 불포함(대소문자 무관), 행동 힌트 5종(title, readOnlyHint, destructiveHint, openWorldHint, idempotentHint) 전부 명시, 설명은 영문 위주로 서비스명 영·국문 병기("naeryeo(내려)") 포함 1,024자 이내.
- **FR-007**: 도구 결과는 원본 백엔드 응답(JSON)이 아닌, 정제된 마크다운 텍스트여야 한다. 소요 시간·환승 횟수·구간별 안내·(가능 시) 요금을 포함하고 크기를 최소화한다. 광고성 문구를 포함하지 않는다.
- **FR-008**: 도구 호출은 p99 3,000ms 이내에 응답해야 한다. 백엔드 호출에는 이 예산 안에서 타임아웃이 설정되어야 하고, 예산 초과 시 사용자 친화적 오류로 응답한다.
- **FR-009**: 오류 응답은 내부 구현 정보(백엔드 주소, 스택 트레이스 등)를 노출하지 않아야 하며, 사용자가 다음 행동을 알 수 있는 한국어 안내를 제공해야 한다.
- **FR-010**: 원격 모드의 모든 도구 호출은 구조적 로그로 기록되어야 한다(요청 식별자, 소요 시간, 성공/실패 구분 포함).
- **FR-011**: 서버 생존 확인용 헬스체크 수단을 제공해야 한다.
- **FR-012**: 저장소 루트에 컨테이너 빌드 정의(Dockerfile)를 제공해야 한다. PlayMCP in KC의 "Git 소스 빌드"가 그대로 빌드할 수 있어야 하고, linux/amd64 대상으로 동작하며, 컨테이너 기동 시 원격 MCP 서버가 시작되어야 한다.

### Key Entities

- **경로(Itinerary)**: 출발지→도착지의 안내 단위. 총 소요 시간, 환승 횟수, 구간 목록을 가진다.
- **구간(Leg)**: 경로의 한 단계. 이동 수단(도보/지하철/버스 등), 승·하차 지점, 소요 시간을 가진다.
- **장소(Place)**: 사용자가 말한 이름이 해석된 위치. 이름과 좌표를 가진다.
- **라우팅 제공자(Routing Provider)**: 경로 검색을 수행하는 교체 가능한 계약. ODsay(로컬)와 MOTIS(원격) 두 구현이 존재한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: PlayMCP AI 채팅(또는 표준 MCP 클라이언트)에서 "강남역→홍대입구역" 질의 시 구간별 안내가 포함된 경로 답변을 받는다 — API 키 등 사전 준비 없이.
- **SC-002**: 대표 질의 세트(수도권·광역시·시외 포함 10건)에 대해 99%의 도구 호출이 3초 이내에 응답한다.
- **SC-003**: MCP Inspector 표준 점검에서 도구 메타데이터(이름 규칙, 행동 힌트 5종, 설명 규격) 관련 지적 사항이 0건이다.
- **SC-004**: 기존 로컬 stdio·CLI 테스트 스위트가 100% 통과한다(회귀 0건).
- **SC-005**: 저장소 URL만으로 컨테이너가 빌드·기동되고, 플랫폼의 서버 정보 조회("정보 불러오기")가 성공한다.
- **SC-006**: 라우팅 백엔드 중단 상태에서도 도구 호출이 3초 이내에 정중한 오류 안내로 응답하고 서버는 살아 있다.

## Assumptions

- **장소명 해석은 MOTIS 내장 지오코딩을 기본으로 사용한다** (OSM 기반, 별도 키·약관 부담 없음). 한국 장소명 해석 품질이 수용 불가로 판명되면 서버측 Kakao Local 키로 대체하는 결정을 별도로 내린다 — 이 대체는 본 스펙의 범위 밖 후속 결정이다.
- 라우팅 데이터(KTDB 전국 GTFS, 2023-03 기준)의 신선도 한계는 알려진 제약으로 수용한다. 데이터 갱신은 본 기능의 범위 밖이다.
- MOTIS 백엔드 서버 자체의 프로비저닝·운영(VM, 데이터 적재)은 별도 인프라 작업(GYE-176)이며 본 기능의 범위 밖이다. 본 기능은 "MOTIS 엔드포인트가 주어졌을 때"를 전제한다.
- PlayMCP 등록·심사·전체 공개·예선 접수 절차는 수동 작업이며 범위 밖이다.
- 본선용 Kakao Tools Widget은 범위 밖이다.
- 원격 모드의 도구는 경로 검색 1종으로 시작한다(가이드 권장 3~10개 대비 적으나 허용 범위). 추가 도구(출발 시간표 등)는 후속 결정.
- 사용자 개인정보를 다루지 않으므로 사용자 인증(OAuth)은 불필요하다.
- 응답 언어는 한국어를 기본으로 한다(대상 사용자가 한국 대중교통 이용자).
